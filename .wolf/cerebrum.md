## Key Learnings
- [2026-07-29] **Vocab-key storage: annotation_jsonb is canonical/authoritative; questions.<key> columns are denormalized copies that drift.** `question_annotations.annotation_jsonb` is the LLM's per-question classification and is the source of truth for grammar_role_key / skill_family_key / stimulus_mode_key / stem_type_key. The matching `questions.*` columns (stimulus_mode_key, stem_type_key) get out of sync (293 rows disagreed pre-repair). Before repairing stray values, check BOTH locations and align column<-annotation rather than hand-mapping. Note which one each consumer reads: practice recall filters on `questions.stimulus_mode_key` (column); diagnostic blueprint slots key off `annotation_jsonb` grammar_role_key/skill_family_key. stimulus_mode_key (format) and stem_type_key (task) are orthogonal — never derive one from the other.

- [2026-07-29] **Distinguishing 'code is broken' from 'worker state is corrupt' under live-reload:** SQLAlchemy 2.0.x mapper state can be poisoned by uvicorn `--reload` re-importing mappers in-place when multiple interdependent model files change in one batch (no clean registry teardown). The poisoned worker then 500s on every `commit()` with a low-level `unitofwork` TypeError that looks like a model-definition bug. The decisive test: run the SAME commit path in a fresh interpreter/process inside the same container — a clean COMMIT proves the source/DB are correct and only the live worker is corrupt, so the fix is a process restart, not a code change. Always try the fresh-process repro before editing models when a `--reload` worker throws internal SQLAlchemy unitofwork TypeErrors.

- **Test02_ENG_Sec01_Mod02A passage text can be repaired from the canonical `Test02` module-02 row (2026-07-28)** — `Test02_ENG_Sec01_Mod02A` q1-27 are missing `current_passage_text` / `question_versions.passage_text` for most questions because ingestion stored the passage sentence inside `current_question_text`. - **Deleting a `questions` row requires FK-safe ordered surgery (2026-07-27)** — almost all FKs to `questions` are `NO_ACTION` (only `span_review_queue` cascades). A doomed question's tree: `question_options` (FK to question_id AND question_version_id), `question_annotations` (FK to question_version_id→versions), `question_versions`, plus `admin_question_audit_logs` references BOTH `question_id` and `question_version_id`. Safe order in one txn: (1) reassign audit logs to the surviving twin (question_id + question_version_id), (2) null doomed question's `latest_annotation_id`/`latest_version_id`, (3) null any OTHER question pointing at a doomed version/annotation, (4) DELETE options → annotations → versions → questions. Keep-rule for dedup by priority: has user_progress > has audit log > practice_status='active' > earliest created_at. Back up all four trees to `backup_*_<date>` tables first. See bug-789 (PT9 triplication).
